# Analytics reporting population

The canonical row predicate is `public.analytics_reporting_eligible_v1(scope, environment, traffic_class)`. Reports apply it to each primary event table **before** grouping, ranking or counting sessions. The trusted server accepts only `business` and `diagnostic` through `src/lib/analytics/reporting-scope.ts`; the SQL RPC validates the same closed set. `business` is the default. The project key is separately server-owned; it is not an environment.

| Source | Environment and class contract | Population |
| --- | --- | --- |
| `analytics_cookieless_events` | Both `NOT NULL`; environments `production`, `staging`, `preview`, `development`; classes `external`, `internal`, `test`, `bot` | Business: only `production` + `external`. Diagnostic: all accepted rows. |
| `analytics_events_v2` | Both `NOT NULL`; same live values, plus migration-era `unknown` and `unclassified` | Same predicate. Legacy `unknown`/`unclassified` is diagnostic only. |
| `analytics_quality_exceptions` | No environment or traffic-class columns | Diagnostic pipeline observations. Realtime's exception count and Data Quality remain all-traffic in either Realtime scope. |

`analytics_sessions_v2` carries the same environment and class contract as consented events, but Realtime counts a session only when it has at least one *qualifying accepted event* in the selected window. This prevents a technical-only session from entering Business. SQL also treats hypothetical `NULL` classification as non-business; the current primary table constraints prohibit it. No historical backfill is performed.

The server derives environment from deployment configuration and request host in `tracking-context.ts`. For consented events it derives class from verified, signed test/internal flags, then the existing conservative bot check, then `external`. The public request cannot set those flags or eligibility. Cookieless ingestion derives environment the same way and currently distinguishes only the existing bot check from `external`; it cannot distinguish a production-hosted internal/test browser without adding a new classification mechanism. The local E2E runner explicitly uses `preview`, so ordinary browser events from E2E are excluded in both tables. Signed test/internal classification applies to consented traffic. No new tracking data or heuristic is introduced here.

Rows previously generated by an E2E runner configured as `production` + `external` are indistinguishable from genuinely eligible traffic by these stored dimensions. The reporting predicate cannot safely reclassify them, and this slice does not backfill or delete them. This is a limitation for historical local data and for any future production-hosted test without a reliable existing classification.

`/admin/realtime` uses Business by default and offers the closed Diagnostic population for investigation. Its event counts, mode split, active consented sessions, pages, observed sources, campaigns, tracking links and destinations all derive from one filtered event CTE. DebugView retains all accepted events and quality exceptions. Data Quality retains all-traffic pipeline counts. Future acquisition, funnel, path and attribution reports should reuse the SQL predicate, while defining their own metric-specific rules.

The local EXPLAIN on an empty reset database used the existing `analytics_cookieless_events_quality_range_idx` and `analytics_events_v2_quality_range_idx` for the rolling-window reads; classification was a filter. This is not evidence for a new index at current scale. Recheck plans with representative production-sized local data before adding one.
