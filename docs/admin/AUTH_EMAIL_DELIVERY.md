# Admin Auth email delivery

Status: local foundation complete; Resend sending domain and DNS configured on 2026-09-29, with Resend verification pending. **No Supabase/Vercel remote configuration, API key, owner account, deployment, or push was performed in this slice.**

## Boundaries and current login

Authentication is Supabase Auth. `/admin/login` calls `signInWithOtp` with `shouldCreateUser: false` after a server-side eligibility lookup. An ineligible address gets the same visible sent state and no Auth call. The callback is exactly `/auth/callback`; `exchangeCodeForSession` uses the PKCE verifier stored by the SSR client in the browser that requested the link. The server reconciles membership and returns either `/admin` or a generic login error. Logout calls `supabase.auth.signOut`. Missing/inactive membership is denied, regardless of a valid Auth session.

Authorization remains the existing `admin_profiles`/RBAC model. `owner`, `admin`, `viewer`, invitation acceptance, audited owner transfer, and the first-owner bootstrap RPC are unchanged. A valid email token alone gives no Admin access. A new-user invitation uses `inviteUserByEmail` and `/auth/confirm?token_hash=…&type=invite`; `verifyOtp` runs server-side, then reconciles the current pending invitation. Existing confirmed users use normal magic-link login.

## Delivery architecture

Supabase Auth → HTTPS Send Email Hook → `supabase/functions/send-admin-auth-email` → React Email HTML + text → Resend `POST https://api.resend.com/emails`.

Supabase creates and verifies all Auth tokens. The function does not generate tokens or expose a generic email endpoint. It verifies the Standard Webhooks signature and timestamp before parsing the payload. Only `magiclink` and `invite` are accepted. The signed recipient comes from `user.email`; subject and template are selected by a closed type map. `token_hash` is used only for the appropriate Supabase verify URL or the existing server invite confirmation route. The hook's `redirect_to` must have an exact configured origin and the exact `/auth/callback` or `/auth/confirm` path, with no query, fragment, userinfo, or wildcard origin. Default allowed origin is `https://pozanuta.pl`; local/Preview origins must be explicitly configured for a hook-enabled environment. Supabase's own Auth Redirect URLs must separately allow each actual redirect.

The production sender defaults to `Poza Nutą <no-reply@auth.pozanuta.pl>` and can be overridden by `AUTH_EMAIL_FROM` for a verified sending domain. Configure `RESEND_API_KEY`, `SEND_EMAIL_HOOK_SECRET` (`v1,whsec_…` generated by the Supabase Auth Hooks UI), and optionally `AUTH_EMAIL_FROM` and `AUTH_EMAIL_ALLOWED_ORIGINS` as **Supabase Edge Function secrets only**. `SUPABASE_URL` is supplied by the Edge runtime. None belongs in `NEXT_PUBLIC_*` or Vercel. The application still needs `NEXT_PUBLIC_SITE_URL=https://pozanuta.pl`, its existing Supabase URL/publishable key/secret key, and temporary `BOOTSTRAP_OWNER_EMAIL` in Vercel server configuration; no Resend key belongs there.

The template is Polish, text-led, and independent of remote images/CSS. It has a descriptive CTA, visible raw-link fallback, one-time/limited-validity wording without a hard-coded duration, and a separate plain-text body. No tracking pixel, UTM, marketing link, or instrumentation is added. Resend has no tracking subdomain configured for `auth.pozanuta.pl`; domain-level open and click tracking are therefore not active. The tracking creation form defaults to click tracking on and open tracking off, but it was not submitted. Recheck this setting before enabling delivery so the provider does not inject an image or replace the Auth link with a tracking redirect.

## Resend sending domain and DNS

The existing Resend account contains exactly one `auth.pozanuta.pl` sending domain, created in the Ireland (`eu-west-1`) region on 2026-09-29. Sending is enabled and receiving is disabled. The intended sender is `Poza Nutą <no-reply@auth.pozanuta.pl>`; it must not be used until Resend marks the domain **Verified**. Resend currently reports **Pending** while checking DNS. No Auth email was sent.

Cloudflare is authoritative for `pozanuta.pl`. These exact Resend-supplied records were added to the existing zone, with TTL Auto and both CNAME records set to DNS only:

| Type | Hostname | Purpose |
| --- | --- | --- |
| TXT | `resend._domainkey.auth.pozanuta.pl` | Resend DKIM domain verification |
| CNAME | `rsend.auth.pozanuta.pl` | Resend SPF/sending configuration |
| CNAME | `send.auth.pozanuta.pl` | Resend sending configuration |

The authoritative Cloudflare nameserver returns all three records. The apex Zoho MX records (`mx.zoho.eu`, `mx2.zoho.eu`, `mx3.zoho.eu`), apex Zoho SPF and verification TXT records, `zmail._domainkey.pozanuta.pl`, and the Cloudflare nameservers remained intact. Normal mail routing for `hello@pozanuta.pl` was not changed. Resend lists DMARC as optional; no DMARC record or policy was added or changed. No Resend API key was created.

The handler uses the signed webhook ID as Resend's 24-hour idempotency key. Resend's non-2xx, network failure, or 3.5-second timeout returns a generic error to Supabase Auth; the app shows its existing generic `send-failed` or invite failure state. The hook does not silently claim delivery. Logs contain only message type, provider outcome category, and signed webhook ID. They do not include email, token, URL, body, provider response, or API key. A provider acceptance is not proof of inbox delivery; later operational monitoring must distinguish those states.

Unsupported message types (`signup`, `recovery`, `email_change`, etc.) fail closed. Open signup is disabled in the current app. Password recovery and email change are not part of the present passwordless Admin flow. Do not enable flows that emit those messages until templates and security handling are added.

## Local workflow and verification

`supabase/config.toml` retains local Mailpit SMTP and does **not** activate the Send Email Hook. Existing E2E obtains local Auth messages from Mailpit and exercises the actual same-browser PKCE callback and invitation confirmation. `src/lib/admin-auth-email-hook.test.ts` signs deterministic hook payloads and mocks the Resend HTTP call; it sends no external email. The function has `verify_jwt = false` only because Supabase Auth calls it without a user JWT; the signed hook secret is mandatory. No browser or public app route can send arbitrary messages through it.

Run `npm run verify`, `npm run test:e2e:local -- tests/e2e/admin-local.spec.ts` with the local Supabase stack, relevant Auth security tests, and `git diff --check`. For a local function smoke check, serve the function with a dummy key and secret and assert that an unsigned request returns 401; do not invoke a signed delivery with a real provider key. Never use a remote Supabase project for these tests.
