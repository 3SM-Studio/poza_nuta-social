The owner expressly deferred destructive purge jobs pending a separate safe implementation slice. These periods still need legal review for sufficiency and exceptions.

| Data category | Approved maximum / trigger | Current technical enforcement and gap |
| --- | --- | --- |
| Cookieless analytics events | Do 90 dni od zdarzenia | **No purge**. Current referrer host, path and UTM remain in rows. |
| Consented raw analytics events | Do 12 miesięcy od zdarzenia | **No purge**; events reference sessions with `ON DELETE RESTRICT`. |
| Pseudonymous visitor | Do 12 miesięcy od ostatniej aktywności | Browser cookie lasts only 180 days; server `analytics_visitors` has no purge. Longer server maximum does not extend browser tracking. |

**TECHNICALLY ENFORCED:** browser cookie expiry as inventoried; 30-minute session validity marker; 7-day invitation validity marker; consent-evidence `expires_at` marker at 180 days. The markers invalidate/flag use but **do not purge rows**. **DOCUMENTED POLICY ONLY:** all approved server periods above until a separately reviewed implementation exists. **NO RETENTION CONTROL CURRENTLY EXISTS** for automatic cleanup of the application tables in the matrix. There is no self-service subject deletion, anonymization or Admin/Auth deletion workflow. Vercel/Supabase infrastructure log retention is separately provider-controlled and account settings were not established here.

The owner approved the three remaining categories on 2026-09-29. The `analytics_quality_daily` schema contains only date, environment, metric name, route, count and update time; current migration writers use the fixed route value `ingest`. Thus the stated non-identifying condition holds **for the current schema and writers**. Recheck actual Production schema and writers before applying the 24-month rule. The current `src` code calls V2/current reporting RPCs, not the legacy `analytics_dashboard`/`analytics_dashboard_range` RPCs; those older functions still exist in migration history. No remote dependency audit, migration-result verification or rollback decision was performed, so the legacy 90-day clock **has not started**. An approved purge needs idempotent, auditable implementation and tests on a copy. Foreign keys matter: deleting `analytics_visitors` sets `analytics_sessions_v2.visitor_id` and `analytics_events_v2.visitor_id` to null, **but consent evidence keeps its `visitor_id`**; deleting a session while events refer to it is restricted. Deleting an Auth user cascades `admin_profiles`, sets invitation `auth_user_id` and referral `linked_user_id` to null, but an `admin_invitations.invited_by` reference restricts deletion; `audit_log.actor_user_id`, `actor_email` and JSON snapshots remain. These are schema effects, not an approved deletion procedure; no destructive cleanup was run.

## Data-subject request procedure (operational draft)

1. Receive access, correction, deletion, objection, restriction or consent-withdrawal requests at `michal.szwindowski@pozanuta.pl` (or forward from `hello@pozanuta.pl`). Record received date, request type, minimum contact needed, verification steps, systems checked, decision, response date and any provider follow-up in the existing controlled mailbox; no ticketing system is claimed. Target the statutory response timetable; [EDPB SME guidance](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_pl) describes a one-month response and limited extension conditions.
2. Verify identity proportionately before disclosing or changing identifiable data: reply to the known correspondence/Admin address or use an existing authenticated path if available. Ask for more only where reasonable doubt exists; do not demand an ID scan by default. Do not ask for new browsing history or a visitor ID unless the requester already has it and it is needed to locate records.
3. Scope the request by system: Zoho correspondence; Supabase Auth, Admin profile, invitations and audit if an Admin; Resend delivery metadata for a known Auth message; consent evidence and consented analytics only if a reliable browser visitor identifier can be provided; Vercel/Supabase infrastructure logs and Cloudflare/Zoho provider data when relevant. Search by known email/record keys, not speculative joins.
4. Explain limits: independent cookieless events carry no visitor/session key and usually cannot be reliably tied back to a requester. A pseudonymous browser UUID is not inherently a person identity; without a reliable link, do not disclose or erase arbitrary rows. Do not falsely promise erasure of every historical event on consent withdrawal. The browser control immediately stops new identified analytics and removes identifiers; existing server records follow an evaluated request and approved retention policy.
5. For a verified request, export/correct/restrict only the relevant rows and correspondence. Before deletion, inspect foreign keys, audit/legal holds, backup/provider windows and effects on other users; use a reviewed transactional procedure, not ad hoc Production SQL. For an Admin/Auth account, revoke sessions before deletion, preserve the active-owner invariant and resolve invitation references. Inform processors/recipients when legally required and feasible. Record the outcome and a minimal proof of handling without copying sensitive tokens or full messages into the audit note.
6. Respond in clear Polish with action taken, justified limits, and complaint route to the Polish data-protection authority. Any refusal, retention exception, objection or transfer question requiring interpretation goes to legal review. Never send Auth tokens, full session values or other users' records in the response.
